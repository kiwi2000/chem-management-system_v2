# マニュアルを更新してデプロイする

このシステムのマニュアルは**公開しているサーバーから配っている**。読んでいる人が見るのは
常に反映済みのものなので、**マニュアルとデプロイは必ずセットで動かす**。

## 0. いつ始めるか

**ほかの作業が進行中なら、その作業を全部終えてから始める。**途中で出すと、
できかけの変更が本番に載るか、あとから出したぶんの変更履歴だけが抜ける。
指示が「終わったらデプロイして」なら、コミットまで済ませてからこの手順に入る。

## 1. 何を出すのかを確かめる

前回のデプロイ記録は `Record this deploy in the change log` という件名のコミット。

```bash
git log --format="%H %s" | grep "Record this deploy in the change log" | head -1
```

それ以降が今回出すもの。作業ツリーが汚れていないことも見る。

**この目印は当てにしすぎない。**変更履歴を機能のコミットに含めてしまうと、印が残らず
1回ぶん多く数えてしまう（実際に起きた）。**必ず `railway deployment list` の時刻と
コミットの時刻を突き合わせて確かめる。**

```bash
railway deployment list
```

```bash
git log --format="%h %ad %s" --date=format:"%m-%d %H:%M" -8
```

いちばん上の SUCCESS の時刻より後のコミットが、今回出すもの。

## 2. マニュアル本体を直す

`apps/web/app/spec/` 以下。変更が利用者の操作に関わるなら、該当ページを直す。

- 読み手は**一般の利用者**。化学物質管理は知っているが、IT の用語は使わない
- 操作の手順を先に書く。理屈は後
- 画面に出る文言と、マニュアルの文言を食い違わせない
- 決め打ちの値を書かない（例：パスワードの桁数は設定で変わるので書かない）

## 3. 変更履歴に1件足す

`apps/web/app/spec/changes/page.tsx` の**先頭**に `<Section>` を足す（新しいものが上）。

- 読み手は**テストに協力している利用者**。開発の記録ではない
- 「前に触ったときから何が変わったか」「操作を覚え直す必要があるか」を伝える
- **不具合の修正も書く。**「どうなっていたか → いまは」の対比が伝わりやすい
- 覚え直しが要るものは `操作が変わったところ` として先に出す
- 見出しは `YYYY-MM-DD　内容`。同じ日に複数回出すなら `（2回目）` を付ける
- **ここに書き足すのはデプロイのときだけ。**作業のたびに書くと、まだ出していないものが載る
- **利用者の画面に出ないものは書かない。**スクリプト・スキル・内部の作りの直しなど。
  読み手が知っても何もできないものを並べると、本当に読むべき行が埋もれる

## 4. 保留事項を増減させる

`apps/web/app/spec/pending/page.tsx`。できあがったものは消す（変更履歴のほうへ移る）。
取り下げになったものも消す。

## 5. 検証

```bash
npm run typecheck
```

```bash
npx eslint .
```

```bash
npx prettier --check .
```

```bash
npm test
```

そのうえで、開発サーバーを立ててマニュアルのページを実際に開き、
**書いたとおりに出ているか**を見る。特に見出しの並び順と、新しい節が出ていること。

## 6. コミットしてデプロイ

**変更履歴の更新は、必ず単独のコミットにする。**件名は
`Record this deploy in the change log`。機能のコミットに混ぜると、次回この印を探せない。

```bash
railway up --detach
```

## 7. 反映を確かめる

```bash
railway status
```

`railway up` が出したデプロイIDと、`railway status` の `deployment ID` が一致し、
status が `Online` になっていれば反映済み。

- **配信ファイルのハッシュで判断しない。** CSS を触っていない変更ではハッシュが変わらず、
  「まだ出ていない」と読み違える（実際に20分待った事故がある）
- **マニュアルの中身は外から確認できない。**ログインが要るため。
  利用者に「変更履歴の先頭を見てください」と伝えて締める

## 8. GitHub に push する

デプロイが `Online` になったら、同じ内容を GitHub にも送る。
**Railway へのデプロイは git push とは別**（作業ツリーを直接送っている）ので、
これをしないと、ソースの控えがこのPCと Railway のビルドにしか無い状態が続く
（実際に2週間・379コミットぶん溜まっていた）。

```bash
git push origin main
```

```bash
git status -sb
```

`## main...origin/main` に `ahead` が付いていなければ済み。

- ブランチは main ひとつ。**force は使わない**
- push は反映の確認（7）の**後**にする。ビルドが失敗したら直してから、失敗した版を
  GitHub に残さない
- 認証の都合で push できなかったときは、そこで止めて利用者に伝える。デプロイ自体は
  済んでいるので、やり直さない

## この環境の制約

- `railway run` / `railway ssh` は自動承認の対象外で**使えない**。本番DBは触れない。
  データの操作が要るときは、画面から実施してもらう
- ローカルDBの検証データは、`scripts/seed-sample.ts` で入れ直せる
  （`--remove` で消える。`SB-` / `MT-` / `PR-` のコードだけを対象にする）
- 開発サーバーが動いている間に `prisma generate` や `next build` を走らせると
  `.next` が壊れる。先に止める
- **本番のDBにはトンネルで繋げる。** `DATABASE_URL` は
  `postgres.railway.internal` なので直接は届かないが、次のコマンドで
  暗号化トンネルが開く（公開プロキシを有効にする必要はない）。

  ```bash
  railway connect Postgres --tunnel-only
  ```

  出力の `postgresql://...127.0.0.1:<ポート>/railway` を一時ファイルに書いて、
  `node --env-file=<一時ファイル> node_modules/tsx/dist/cli.mjs <スクリプト>` で流す
  （`node_modules/.bin/tsx` はシェルの薄皮なので `node` から直接は動かない）。
  終わったらトンネルを閉じ、一時ファイルを消す。

  **本番に書き込む前に、必ず現状を読んで確かめる。**とくに、投入スクリプトが
  消す対象（`SB-` / `MT-` / `PR-` で始まるコード）に既存データが無いこと
