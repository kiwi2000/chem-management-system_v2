# 0002. 多言語はソース内の辞書で管理する

日付: 2026-08-13 / 状態: 採用

## 背景

日英切替を最初から全画面で行う方針になった。文言の置き場所として、
(a) ソース内の辞書ファイル、(b) DB＋管理画面、(c) 両方（DBで上書き）の3案があった。

v1 は (b) に近い作りで、DBのカタログをクライアントから取得して `t(key, fallback)` で引いていた。
このやり方には次の弱点があった。

- 訳の抜けに気づけない（fallback の日本語がそのまま出るだけ）
- カタログ取得が完了するまで日本語が見え、切り替わる瞬間にチラつく
- サーバーコンポーネントやAPIのエラーメッセージからは使えない

## 決定

**(a) ソース内の辞書**を採用する。

- `packages/shared/src/i18n/ja.ts` がキーの正本。`export type Messages = typeof ja`
- `en.ts` は `const en: Messages = {...}` と型注釈するため、**キーの抜けはビルドエラーになる**
- 文言はキー文字列ではなくオブジェクトを辿って使う（`m.login.submit`）。綴り間違いも型で落ちる
- 引数を取る文言は関数にする（`m.errors.loadFailed(404)`）
- ロケールはサーバーで確定させてから描画するため、チラつきも取得のための通信も無い

あわせて DB の `locales` / `ui_translations` テーブルを廃止し、
ユーザーの表示言語は `users.preferred_locale`（"ja" / "en" の文字列）で持つ。

### 適用範囲

画面のラベル・ボタン、エラーと確認メッセージ（Zodスキーマ・authz・APIルートを含む）、
マスタの名称（日本語名・英語名の2列を `pickName()` で切替）、生成する帳票・TSV。

### 切替の挙動

- ロケールの優先順位: Cookie `chem_locale` → ログインユーザーの設定 → 既定（ja）
- Cookie を先に見るのは、**ログイン前に選んだ言語をログイン画面でも保つ**ため
- 切替時は Cookie とユーザー設定の両方を更新するので、両者は基本的に一致する
- `PUT /api/locale` は認証不要（ログイン画面でも切り替えられる必要があるため）。
  副作用は Cookie と自分の設定だけで、業務データには触れない

## 結果

- 訳の抜けが `tsc` で落ちることを実際に確認した（en から1キー消す → TS2741）
- 文言の変更にはデプロイが必要になる。運用で現場が直接直したくなったら
  「既定は辞書、DBに上書きがあれば優先」の (c) へ後から拡張できる（辞書側の型はそのまま使える）

## 影響

`@chem/shared` の Zod スキーマは辞書を受け取る**関数**になった（`loginSchema(m)`）。
今後スキーマを追加するときも同じ形にすること。
