# 0003. 権限は役割ではなく権限そのものをユーザーに持たせる

日付: 2026-08-14 / 状態: 採用

## 背景

これまでは役割（システム管理者 / 特権 / 非特権）＋編集可フラグの4段階だった。
実際の運用では「製品は編集するが法規制は見るだけ」「出力だけはさせたくない」といった
組み合わせが必要で、4段階では表現できないことが分かった。

## 決定

役割をやめ、**13個の権限**をユーザーに直接持たせる（`user_permissions` 中間テーブル）。

製品を見る／非公開の製品も見る／製品を編集（組成の編集を含む）／組成を見る／非公開の組成も見る／
物質を見る／物質を編集／法規制を見る／法規制を編集／データを出力／
お知らせを投稿／他人のお知らせも編集・削除／システム管理

### 判断したこと

- **判定の実行・逆引き検索は「製品を見られる」に含める。** 結果を見るだけで、新しい情報は生まれない
- **データ出力（TSV・帳票）は独立させた。** 画面で見るのとファイルで持ち出せるのはリスクが違う
- **金属換算係数・情報源・リンクバージョンは「法規制を編集できる」に含める。** 判定のパラメータであり、
  法規制と切り離して管理する場面が無い
- **監査ログの閲覧はシステム管理に含める**
- **非公開（機密）フラグは残す。** 「この製品だけ隠す」は製品単位のフラグでしか表現できないため、
  権限は「非公開のものも見られる」という上位の閲覧権限として設ける
- **システム管理は他の権限を含意しない。** 管理者でも業務データの権限は別途付ける
  （運用上は「システム管理者」プリセットで全部入る）

### 含意（依存）

「編集できるが見られない」は成立しないので、付与時に自動で補う。
補った結果を保存するので、判定側は集合に入っているかを見るだけで済む。

| 付けると | 一緒に付く |
|---|---|
| 製品を編集 | 製品を見る、組成を見る（組成編集を含むため） |
| 非公開の製品を見る | 製品を見る |
| 非公開の組成を見る | 組成を見る |
| 物質を編集 | 物質を見る |
| 法規制を編集 | 法規制を見る |
| 他人のお知らせを編集 | お知らせを投稿 |

画面では逆方向も連動させる（前提を外すと、それに依存する権限も外れる）。

### 役割マスタを作らなかった理由

管理画面で役割を定義して割り当てる案もあったが、画面が1つ増えるわりに、
利用者数がそれほど多くない環境では効果が薄い。
代わりに**プリセットボタン**（閲覧のみ / 一般担当 / 法規制担当 / システム管理者）で
チェックを一括投入し、そのあと個別に調整できるようにした。
必要になれば、プリセットを役割マスタへ昇格させる形で後から拡張できる。

## 締め出しの防止

- 自分自身から管理権限を外せない／自分自身を削除できない
- 有効なシステム管理者が0人になる操作は 409 で拒否する
- 権限を変更したら対象ユーザーのセッションを切る（縮小をその場で効かせるため）

## 結果

- 移行時、既存の役割を権限へ機械的に置き換えた（マイグレーション `20260814090000_permissions_and_news`）
- 認可の呼び忘れを検出するテストを入れた（`apps/web/lib/authz-coverage.test.ts`）。
  認可を通していない route.ts を1本置いて、実際に落ちることを確認済み
