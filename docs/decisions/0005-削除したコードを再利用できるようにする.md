# 0005. 論理削除したコードを再利用できるようにする

日付: 2026-08-14 / 状態: 採用

## 背景

v1 では物質を論理削除（`deleted_at` を立てる）しても、正規化コードの一意制約が残り続けたため、
**同じコードを二度と登録できなかった**。「間違えて登録したので消してやり直す」ができない。
（金属換算係数だけは削除済みレコードを復活させる処理があり、扱いが非対称だった）

## 検討した案

1. **部分ユニークインデックス**（`WHERE deleted_at IS NULL`）
   PostgreSQL では素直だが、MySQL と SQL Server にはこの構文が無い。移植性の方針に反する
2. **`(code_normalized, deleted_at)` の複合ユニーク**
   NULL の扱いがDBごとに違う。PostgreSQL は NULL 同士を別物とみなすため、
   **未削除の行に同じコードを何個でも作れてしまう**。一意制約の意味が壊れる
3. **削除時に正規化コードを退避する**

## 決定

案3を採る。論理削除するとき `code_normalized` を `<正規化コード>:<id>` に書き換える。
表示に使う `code` は原文のまま残すので、監査ログや過去の参照から元のコードは追える。

```
削除前: code = "PB-001", code_normalized = "PB-001"
削除後: code = "PB-001", code_normalized = "PB-001:cmsrvz0p9000atgv8qzf9kzl3"
```

`code_normalized` の桁を 64 文字にしてあるのはこの退避のため（コード自体は 20 文字）。

## 結果

削除 → 同じコードで再登録できることを実測で確認した。
DB固有の機能を使っていないので、MySQL / SQL Server へ切り替えてもそのまま動く。

## 影響

- 削除済みレコードを「復活」させる機能を作るときは、正規化コードを戻す処理が要る。
  そのとき既に同じコードが使われていれば衝突するので、復活は「コードを指定し直す」形にすること
- 同じ扱いを他のマスタ（製品・法規制など）にも適用する。S6 以降で踏襲する
