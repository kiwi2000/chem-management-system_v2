# S28 100 名規模の手当て（2026-10-17）

利用者の上限を 20 名ほどから 100 名へ上げるにあたり、作りで直す所を洗い出した（会話での検討）。
結論は「作りは変えなくてよい。小さな手当てが 2 つ」。

## 1. 検討の結果

| 項目 | 結論 |
| --- | --- |
| PDF 作成の同時実行 | 既に待ち行列（同時 1 件）だった。足りないのは「1 件ものが、まとめて作る大きな仕事の後ろで待たされる」こと → §2 |
| 判定の再計算 | 手を入れない。運用で守る（利用者の少ない時間に行う・やり直す前に知らせる）。人数の警告は作らない（利用者決定） |
| アクセス記録の量 | 保存期間をシステム設定で決め、1 日 1 回自動で片づける → §3 |
| 書類の「20 名ほど」 | 100 名相当の負荷を測ってから書き換える（未） |
| DB の接続数・セッションの確認 | 変えなくてよい（アプリ 1 台のあいだは PostgreSQL の既定 100 に収まる） |

仕様として別途決めること: 利用者管理のひな型（役割）、社内の認証基盤（AD）との連携、同時編集の衝突（楽観的ロック。§4）。

## 2. 帳票の待ち行列を 2 本にする

`apps/web/lib/doc-batch-lane.ts`、`doc-batch-job.ts`。

- 帳票を作る仕事（1 件ものも、まとめて作るものも `POST /api/documents/batch`）は、**小さい仕事（5 枚以下）と大きい仕事で別の待ち行列**に入る
- それぞれ順に 1 つずつ走る。2 本が同時に動くので、PDF 作成は最大 2 件まで同時
- 同じ待ち行列の中は先着順。どちらにも続きが無くなったらブラウザ（Chromium）を閉じてメモリを返す
- 「小さい」の境目（5 枚）は定数 `SMALL_JOB_UNITS`。設定にはしていない（勝手に決めた点）

## 3. アクセス記録の保存期間

システム設定（管理者のみ）「アクセス記録の保存期間」。`packages/shared/src/settings.ts`、`apps/web/lib/access-log-retention.ts`。

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| アクセス記録を残す日数 | 0（片づけない） | 1 日 1 回、これより古い行を片づける。0 以外は 30〜3650 日 |
| 片づけかた | 書き出してから消す | 「消すだけ」も選べる |
| 書き出し先のフォルダー | `data/access-log-archive` | 相対ならアプリのフォルダーから。保存時に書けるか確かめる |

- **対象は画面の「アクセス記録」に出る行だけ**（ログイン・ログアウト・失敗・2 要素認証とパスキーの付け外し・組成の閲覧・出力・取り込み）。
  手で消すとき（画面の「◯日以上前を削除」）と同じ範囲。**データの作成・変更の記録は残す**（勝手に決めた点。消すなら別途）
- 書き出しは TSV（UTF-8、BOM つき。表計算ソフトでそのまま開ける）。項目は画面と同じ。利用者の名前とメールはこの時点で引いて書く（あとで利用者が消されても読める）。
  ファイル名は `access-log_<最初の日>_<最後の日>_<走った時刻>.tsv`。何も無ければファイルは作らない
- 片づけた事実は、手で消したときと同じ形でアクセス記録の表（`audit_logs`）に残す（`what: 自動（N 日より前）`、件数、ファイル名）
- 書き出したファイルは、アクセス記録の画面の下に一覧が出て、管理者が取り出せる（`GET /api/admin/access-log/archive`、`…/archive/<名前>`）。
  取り出したことも記録に残す。名前は決まった形のものしか受けず、書き出し先の外には出ない
- 走らせるのはサーバーの見回り（`apps/web/instrumentation.ts` → `lib/maintenance-timer.ts`。起動 2 分後と、以後 1 時間おき）。
  1 日 1 回しか走らないように、走った印は DB（`system_settings` の `access_log.retention_state`。画面の設定には出ない）で持ち、
  同時に起こされた実行どうしの取り合いは `updateMany` の件数で決める。前回の結果（時刻・件数・ファイル・失敗の理由）は設定画面に出る
- 5000 行ずつ引いて、書き出し → 消す、を繰り返す（長い lock を避ける）

**置き場所の注意**: `data/` は Docker の保存領域（`compose.prod.yml` の `app-data`）と Windows の更新（`update.ps1` の `/XD`）で守られる。
**Railway には保存領域が無い**ので、書き出したファイルは再デプロイで消える（帳票の出力先と同じ事情）。Railway では「消すだけ」にするか、保存領域を付ける。

## 4. 同時編集（楽観的ロック）の検討（2026-10-17、検討のみ）

いまは後勝ちで黙って上書きする。楽観的ロックに変えることはできる。

- 仕組み: 詳細を返すとき `updatedAt` を一緒に返す（製品・物質の DTO には既にある）。保存のとき画面がその値を送り返し、
  サーバーは `updateMany({ where: { id, updatedAt: 受け取った値 } })` で更新し、件数 0 なら 409「他の人が先に変更しました」を返す。画面は読み直しを促す
- 範囲: 更新の API は 42 か所。全部に入れる必要はなく、**複数の人が画面から直すもの**から。
  先にやるなら 製品・物質・組成（組成は子の表を丸ごと入れ替えるので衝突の影響が大きい）・様式・法規制の区分
- 作業の目安: 先の 5 つで 2〜3 日（API・画面の 409 の扱い・試験）。残りは必要が出たところから
- 行内で直すマスタ（金属換算係数など）は 1 行ずつの更新なので衝突しにくく、後回しでよい

## 5. 確かめたこと（2026-10-17、開発環境）

- 設定画面で 60 日・書き出しを保存 → 再読み込みで残る。片づけを 1 回走らせ、60 日より古い 83 件が TSV に書き出されて消え、
  記録と状態の行が残った。2 回目はその日のうちなので走らない（`skipped: recent`）
- アクセス記録の画面に書き出したファイルの一覧が出て、API で落とせる（`content-disposition: attachment`）。
  名前が決まりに合わないもの（`../../.env`）は 404、ログインなしは 401
- `npm run build`（起動時の入口 `instrumentation.ts` を含む）が通る。型検査・lint・単体試験（車線の決め方、TSV の形、ファイル名）も通過
- 2 本の待ち行列は単体試験と型検査で確かめた。実際に大きな仕事と 1 件ものを同時に流す確認はまだ
- 確認のあと設定は 0 に戻した。開発環境の 8 月 13〜16 日のアクセス記録 83 件は `data/access-log-archive/` の TSV に移った（DB からは消えた）
