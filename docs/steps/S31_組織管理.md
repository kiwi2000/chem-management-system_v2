### 決めたこと（利用者に確かめた）

| 項目 | 決まり |
| --- | --- |

| 選べる組織 | どちらも、投稿する人の組織と、その上の組織。最初は自分の組織が選ばれている |
| 宛先で見える人 | 選んだ組織とその下の人だけ（ほかの部・取引先には見えない） |

| ホームの見出し | 差出元で分ける（「〇〇からのお知らせ」。並びは組織の木の上から、差出元の無いものは最後の「その他のお知らせ」）。各行の右に「〇〇宛て」 |

### 作るときに決めた点

- 直すときは、いま付いている差出元・宛先をそのまま残せる（異動したあと・管理する人が他人の分を直すとき）。新しく選ぶなら自分の組織とその上だけ

- 宛先の外のお知らせは、編集できない人が直接開くと 404
- ホームの各行の右は、投稿者の今の組織をやめて宛先にした（差出元は見出しに出ているため）
- 組織の無い人は投稿できない（画面に案内を出し、保存ボタンを押せない。API は 400）
- 組織は印を付けて消すので、宛先の組織を消しても「全員」には広がらない。外部キーも行ごと消す動きを止めた（RESTRICT）

- 作り: `newsChoices()`（選べる組織＝たどった組織のうち有効なもの）を、選択肢の API と保存の確認だけに使う。見える範囲は今までどおり `newsOrgChain()` の全部。`orgChain()` の中では絞らない（最初に選ばれる権限グループなども使うため）
- 試験: `apps/web/lib/visibility.test.ts` に、無効の組織・日本の日付（世界標準時 15:30 ＝ 日本の翌日）・一覧の絞り込みと並べ替えを足した
- 実測（一時ユーザー 3 人で）: 品質保証部を無効にすると、その人の選択肢は「株式会社ケミカル総研」だけになり、最初から会社が選ばれる。品質保証部を選んで送ると 400。無効にする前のお知らせは差出元・宛先をそのままで直せ、編集の画面の選択肢にも残る。ホームには自分の部宛てが出続ける。監査の記録に差出元・宛先と、全員 → 会社に変えたときの `before` が残る。一覧は管理者が宛先「製造」で 1 件、品質保証部の人が同じ条件で 0 件（宛先の外は絞り込んでも出ない）。宛先「空白」は全員宛てだけ。差出元・宛先で並べ替えられる
- **日付のずれは画面では確かめていない**（日本の 0〜9 時でないと違いが出ない）。試験で確かめた
- マニュアル: 「だれが何をできるか」のお知らせの節に、無効の組織・一覧の列と絞り込み・掲載日の数えかたを足した

### 同じ形の残りも直した（2026-11-12、利用者の指示）

世界標準時の日付を「今日」に使っていた 5 か所と、それに合わせて帳票の題名 2 か所を、日本の日付にした。

- 画面で最初に入る日付: `components/link-version-section.tsx`（版の新規登録の基準日）・`components/rejudge-button.tsx`（再判定の判定対象日の予備の値）
- ファイル名に付ける今日の日付: `app/documents/[templateId]/[targetId]/page.tsx`・`app/api/document-files/…/route.ts`・`app/api/export/route.ts`
- 作った日時から題名の日付を作る所: `app/documents/saved/[id]/page.tsx`・`app/documents/batch/[id]/page.tsx`。上のファイル名と同じ日付になるように一緒に直した（直さないと、日本の 0〜9 時に作った帳票で、ファイル名と題名の日付が 1 日ずれる）
- 作り: `lib/judgement-date.ts` に `dayInJapan(時刻)` を足し、`todayInJapan()` はそれを呼ぶ。試験は `lib/judgement-date.test.ts`
- 実測: データ出力のファイル名と、版の新規登録の基準日に、今日の日付が入る（日本の 0〜9 時でないと直す前との違いは出ないので、違いそのものは試験で確かめた）

### アクセス記録の集計と控えも日本の時刻に（2026-11-12、利用者の指示）

- 集計（`app/api/admin/access-log/stats/route.ts`）: 「1 日に開いた件数」の日を日本の日付に。**時間帯も日本の時刻にした。**`getHours()` はサーバーの時計の地域で決まり、世界標準時で動く Docker・Railway では、時間帯の棒と「夜間のログイン（22〜6 時）」が 9 時間ずれていた（日本の 7〜15 時のログインが夜間に数えられる）。開発の PC と Windows Server は日本の時計なので気づけなかった
- 控え（`lib/access-log-retention.ts`）: ファイル名の期間の日付と、走った時刻を日本の時刻に。中の `at` の列は世界標準時のまま（末尾に Z が付く形で読み違えないため）。前に書き出したファイルの名前は変えない
- 作り: `lib/judgement-date.ts` に `hourInJapan()`・`stampInJapan()` を足した。試験は `lib/judgement-date.test.ts`・`lib/access-log-retention.test.ts`（サーバーの時計を世界標準時にしても通る）
- 実測: 集計の API の時間帯ごとの件数が、DB の側で日本の時刻に直して数えた件数と一致した（9 時 2・18 時 11・19 時 10・20 時 7・21 時 1）。開発の PC は日本の時計なので、直す前との違いは出ない
- 途中で開発サーバーが直す前の部品を使い続け、集計の API が 500 を返した（`hourInJapan is not a function`）。決まった手順で立ち上げ直して直った

見つけたが直していない（利用者に報告した）:
