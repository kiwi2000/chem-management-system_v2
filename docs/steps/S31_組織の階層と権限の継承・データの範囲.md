# S31 組織の階層と権限の継承・データの範囲

2026-10-19〜20 指示。「組織は階層化できる（親は 1 つ、深さは自由、階層の意味は決めない）」「あるグループに設定した権限は、その下のグループにも効く」
「他のグループが作ったデータも見られるグループ（化学物質管理の部署）を作りたい」「矛盾が生じないかは慎重に検討」。
ToDO 5「組成編集・参照権限制御」もこの中で片づける。

## 0. いまの作り（変える前）

- 組織（`organisations`）は平ら。種別（会社・部署・取引先・その他）と自由項目（帳票の差出人などに使う）を持ち、1 人が何件でも所属できる（2026-09-03）
- 権限（`user_permissions`、24 種類）は**人にだけ**付く。含意は付与時に展開して保存し、読むときにも閉じる（S4）
- 製品・組成・添付・帳票に「どの組織のものか」は無い。見える・見えないは「公開済か・自分が作ったか」（`visibilityWhere`）と人の権限だけで決まる
- お知らせの「グループ」（`groups`、kind NEWS）は別の平らな表。お知らせはグループ宛て、人は 1 つのグループ（`users.news_group_id`）のお知らせを読む
- 帳票の差出人・PRTR の所属は、所属する組織を**種別で絞って表示順の先頭**（`pickOrganisation`）

## 1. 考え方

**軸は 2 つ。どちらも「足し合わせ（和）」で、効くときは「かつ（AND）」。**

| 軸 | 何を決めるか | 求め方 |
| --- | --- | --- |
| 操作の権限 | 何ができるか（製品を編集できる、法規制を見られる、…） | 人に付いた権限 ∪ 所属する組織の権限 ∪ その上位の組織の権限。最後に含意で閉じる |
| データの範囲 | どの製品（と、その組成・添付・判定・帳票）を見られる・直せるか | 所属する組織の枝の下 ∪ 「範囲の付与」で指定された組織の枝の下（上位から受け継いだ付与も含む）。**見る**と**直す**は別の集合 |

- ある操作が通るのは、**操作の権限があり、かつ対象がその操作の範囲に入っている**とき
- 「禁止」という設定は無い。だから上下で矛盾しない（上で付けた権限を下で打ち消せない。付けたくなければ上に付けず、付けたい組織にだけ付ける）
- 下への効き方はどちらの軸も同じ向き。**上の組織に付いたものは下の組織に効く。上の人は下のデータまで見える。下の人は上のデータを見られない**（上の組織に範囲を付けない限り）
- **システム管理者（ADMIN）は、範囲が全部。**いまの動き（管理者は全部見える）を変えないため。全製品の判定し直し・出力・裏の仕事も管理者の権限で動くため
- 持ち主の無いデータ（既存の製品すべて）は、いままでどおり全員の範囲に入る。入れた日に見え方が変わらないことを**不変条件**にして試験で守る

言葉: 階層のある組織を「組織」と呼ぶ（「グループ」とは呼ばない。お知らせのグループは組織に統合する。§7）。

## 2. 仕組み

### 2-1. 表

| 表 | 変更 |
| --- | --- |
| `organisations` | `parent_id`（null なら最上位）、`path`（先祖の id を `/` で連ねた文字列。枝の下の検索と並べ替えに使う）、`depth`。同じ親の下で `name_ja` は重ならない（最上位どうしも重ならない。null の親は DB の一意制約で区別されないので API で確かめる）。`code` はいままでどおり全体で一意 |
| `organisation_permissions`（新） | 組織 × 権限。人の `user_permissions` と同じ列挙。含意は付与時に展開して保存 |
| `organisation_scope_grants`（新） | 範囲の付与。`organisation_id`（受ける側）× `target_organisation_id`（見られる側。null なら「全部」）× `mode`（VIEW / EDIT）。**推移しない**（A が B を、B が C を見られても、A は C を見られない） |
| `users` | `primary_organisation_id`（主な所属。新しい製品の持ち主の既定。所属の 1 つでなければならない）。`news_group_id` は廃止（§7） |
| `products` | `owner_organisation_id`（持ち主。null なら全員の範囲）。組成・添付・判定・帳票は製品の持ち主に従う（自分では持たない） |
| `news` | `group_id` → `organisation_id`（null なら全員宛て） |
| `groups` | 廃止（お知らせのグループは組織へ移す） |

物質・法規制・インベントリ・GHS 分類データ・金属換算係数などの共有マスタは範囲の対象にしない（2026-10-20 決定）。

### 2-2. Actor（ログイン中の人）に載せるもの

`getActor` / `actorOf` / `requireUser` で 1 回だけ計算し、`Actor` に持たせる。

```ts
interface Actor {
  user; permissions; has(p);
  scope: {
    view: "all" | Set<orgId>;   // 見られる持ち主の組織の集合（枝の下まで展開済み）
    edit: "all" | Set<orgId>;
  };
  organisations: { id, primary }[];  // 所属
}
```

- 組織の表は小さい（数十〜数百行）ので、要求ごとに全部読んで記憶の中で木を歩く。再帰 SQL は使わない（MySQL / SQL Server へ移せる書き方を保つ）
- `permissions` = expand(人の権限 ∪ 所属組織の権限 ∪ 先祖の権限)。**無効（`active_flag = false`）か消した組織は、権限も範囲の付与も出さない**（§4-5）
- `scope.view` = 所属組織の枝の下 ∪（所属組織と先祖が受けている VIEW/EDIT 付与の対象の枝の下）。`scope.edit` は EDIT 付与だけ。ADMIN なら両方 `"all"`

### 2-3. 見える条件（`visibilityWhere`）

いまの `visibilityWhere(actor)` は同期関数で 27 か所から呼ばれている。同期のまま、範囲の条件を **AND** で足す。

```
見える = 公開状態の条件 AND 範囲の条件
  公開状態の条件 = INACTIVE_VIEW があれば無条件、無ければ（有効かつ公開済）OR（自分が作った）
  範囲の条件     = scope.view が "all" なら無条件、
                   無ければ owner_organisation_id IS NULL OR owner_organisation_id IN (scope.view)
```

- **INACTIVE_VIEW は公開状態の条件だけを緩め、範囲は緩めない**（いまは `{}` を返して全部を通している。ここを変える）
- 「自分が作った」も公開状態の条件の側に置く。作った人は、持ち主が範囲の外へ付け替えられても見え続ける（驚きが少ない。§6 で確認）
- 直せる条件 = `canEditProduct` に `scope.edit` を足す。持ち主の付け替えは、**元の持ち主と新しい持ち主の両方が `scope.edit` に入っている**ときだけ（自分の範囲の外へ押し出す・外から引き込むを防ぐ）
- 製品を返すすべての API がこれを通ることを、機械で確かめる（§8）。組成・添付・判定・帳票・TSV 出力・GHS 判定（SDS 版）は製品を `visibilityWhere` で引いてから中身を返しているので、そのまま範囲が効く（確かめるだけ。作り直しは無い）

### 2-4. 組織を直せる人（権限の昇格を防ぐ）

| 操作 | 要る権限 |
| --- | --- |
| 名前・種別・自由項目・表示順・有効無効 | ORG_EDIT |
| 親の付け替え、組織への権限の付与、範囲の付与 | **ADMIN**（人の権限を直すのと同じ扱い） |
| 所属の変更（誰をどの組織に） | ADMIN（いまもユーザー管理の中） |

ORG_EDIT だけで親を付け替えられると、自分の組織を管理者の組織の下へ移して管理者になれる。だから親・権限・範囲は ADMIN に限る。

### 2-5. 管理者の数え方（締め出し防止）

`isAdminUser` と「管理者が 0 人になる操作は拒否」は、いま `user_permissions` の行だけを見ている。これを**実効の管理者**（人の権限 ∪ 有効な所属 × 有効な組織とその先祖の権限）で数え直す。拒否する操作: 組織から ADMIN を外す、組織を無効化・削除する、所属を外す、人を無効化する、人から ADMIN を外す。
締め出しからの復旧（`scripts/grant-permission.ts`）は人に付ける作りのまま使える。

### 2-6. お知らせ

- 宛先 = 組織（null なら全員）。読める = 全員宛て ∪ 所属組織宛て ∪ その先祖宛て（上の組織のお知らせは下の人にも届く）。**範囲の付与は効かない**（お知らせはデータではなく連絡）
- 投稿できる先 = 所属組織とその下（NEWS_POST）。NEWS_MANAGE は全部
- 1 人 1 グループの制限は無くなる

### 2-7. 帳票の差出人・PRTR の所属

`pickOrganisation`（種別で絞って表示順の先頭）はそのまま。主な所属は「新しい製品の持ち主の既定」にだけ使う。2 つの決め方があるのは意図的（§6 で「差出人も主な所属にするか」を確認）。
PRTR_ENTRY は「所属する組織の分だけ」。上の組織の人が下の組織の分も入れられるようにするかは §6。

## 3. 決めたこと（2026-10-19〜20、利用者）

1. 操作の権限とデータの範囲の両方を組織に付けられる。効き方は上から下へ
2. 持ち主は製品側に持つ。共有マスタは範囲の対象外。既存の製品は持ち主なし＝全員に見える
3. 複数所属は残す。足し合わせ（和）。人ごとの権限も残す。主な所属を 1 つ持つ。管理者の権限も組織に付けられる（「管理者」という組織を作れる）
4. 組織は種別と名前の両方を持つ。種別に階層の意味は無い
5. 親は 1 つ、深さ無制限、同じ親の下で名前は重ならない、下が無いときだけ消せる、親を無効にしたら下も無効扱い（返事なし → 推奨どおり）
6. お知らせのグループは組織に統合する
7. 他の組織のデータを見られる組織を作れる（範囲の付与。見るだけ／直せる。木の位置とは無関係。下へも効く）

## 4. 矛盾が出そうな点と、その扱い

| # | 起きうる矛盾 | 扱い |
| --- | --- | --- |
| 4-1 | 上下で権限が食い違う | 「禁止」が無いので食い違わない。効くのは和。付けたくなければ上に付けない |
| 4-2 | 木を使った権限の昇格（自分の組織を管理者の組織の下へ移す） | 親の付け替え・組織への権限・範囲の付与は ADMIN だけ（§2-4） |
| 4-3 | 持ち主の付け替えで、自分の範囲の外へ出す／外から引き込む | 元と先の両方が `scope.edit` に要る（§2-3） |
| 4-4 | 管理者を組織に付けたら、最後の管理者の守りがすり抜ける | 実効の管理者で数える（§2-5） |
| 4-5 | 親を無効にしたら下のデータが消える | 無効な組織は権限と範囲の付与を**出さない**だけ。その組織が持ち主のデータは、上の組織・範囲を付与された組織・管理者からは見え続ける |
| 4-6 | INACTIVE_VIEW（未公開も見られる）が範囲をすり抜ける | 公開状態の条件だけを緩める（§2-3） |
| 4-7 | 範囲の付与が連鎖して思わぬ広がり（A→B→C） | 推移しない（§2-1） |
| 4-8 | 部署をまたいで使う原材料が「開けない」になり、判定が不完全になる | 原材料は持ち主なし（全員）を既定にするか、製品ごとに「共有」の印を付けるか。**§6 で決めてもらう** |
| 4-9 | 組織を消したあと、その組織が持ち主のデータの見え方が決まらない | 下の組織・所属・持ち主の製品・お知らせ・PRTR・範囲の付与のどれかが残っていれば消せない。付け替えてから消す |
| 4-10 | 権限を変えたらセッションを切る（S4 §6）が、組織の権限を変えると部署ごと切れる | 権限は要求ごとに読み直しているので、組織の権限は次の操作から効く。セッションを切るのは**人の権限を直したときだけ**（S4 §6 はそのまま） |
| 4-11 | 「どの組織か」の決め方が 2 つある（種別＋表示順／主な所属） | 用途が違う。差出人＝種別＋表示順、製品の持ち主の既定＝主な所属。**§6** |
| 4-12 | 同じ親の下の名前の一意制約で、親が null の行が区別されない | API で確かめる（PostgreSQL の一意制約は null どうしを別物と見る） |
| 4-13 | 作った人が、持ち主の付け替えで見えなくなる | 「自分が作った」は残す（見え続ける）。**§6** |
| 4-14 | PRTR の入力は「所属する組織の分だけ」。上の人が下の分を入れられるべきか | **§6** |
| 4-15 | 帳票（`documentWhere`）の範囲 | 対象の製品の範囲に従う。物質だけの帳票は範囲なし。DOCUMENT_VIEW_ALL は従来どおり AND |
| 4-16 | お知らせのグループに所属していて組織に所属していない人 | 開発 DB では 0 人。移行では、グループを同じ名前の最上位の組織にし、その人を所属させる（無ければ作る） |

## 5. 勝手に決めた点（変えたければ言ってください）

- 範囲の付与は推移しない（4-7）
- 無効な組織は権限と付与を出さないだけで、データは消えない（4-5）
- 親・権限・範囲の変更は ADMIN（4-2）
- 持ち主の付け替えは両方の範囲が要る（4-3）
- 実効の管理者で締め出しを守る（4-4）
- 「自分が作った」は範囲に関係なく見え続ける（4-13。§6 で確認も取る）
- 範囲の条件は `visibilityWhere` に AND で足し、同期のまま（27 か所を書き換えない）

## 6. 決めてもらうこと（作る前に）

1. **原材料の持ち主**（4-8）: (a) 原材料は持ち主なしを既定にする（部署をまたいで使えるが、原材料の組成は全員に見える） (b) 製品ごとに「共有」の印（持ち主はあるが、組成を使う判定では誰からも開ける。組成の中身は見えない） (c) 持ち主の範囲どおり（見えない原材料を使う製品は判定が「要判断」になる）。推奨 (b)
2. **作った人の扱い**（4-13）: 持ち主が自分の範囲の外へ付け替えられても、作った人には見え続けてよいか。推奨: 見え続ける
3. **帳票の差出人**（4-11）: いままでどおり「種別で絞って表示順の先頭」か、「主な所属」に変えるか。推奨: いままでどおり（帳票の作りを変えない）
4. **PRTR の入力**（4-14）: 上の組織の人が下の組織の分も入れられるようにするか。推奨: 入れられる（下への効き方と揃える）
5. **お知らせのグループを組織に移すときの種別**: 「その他」＋呼び名「お知らせ」でよいか

## 7. 移行

1. `organisations` に `parent_id`・`path`・`depth` を足す。既存の行は全部が最上位（`parent_id` null、`path` = 自分の id）
2. `organisation_permissions`・`organisation_scope_grants` を作る（空）
3. `users.primary_organisation_id` を足す。所属が 1 つの人はそれを主な所属に。複数の人は `pickOrganisation` の並びの先頭（種別は問わない）を主な所属に
4. `products.owner_organisation_id` を足す（全部 null）
5. お知らせのグループ: `groups`（kind NEWS）を同じ名前の最上位の組織（種別はその他、呼び名は §6-5）として作り、`news.group_id` を `organisation_id` に付け替え、`users.news_group_id` の人をその組織に所属させる。終わったら `groups` と `news_group_id` を落とす（**落とす移行は別の回にする**。先に動かして確かめる）
6. 入れた日の不変条件: 既存の人の見える製品の集合と、できる操作は変わらない（試験で確かめる）
