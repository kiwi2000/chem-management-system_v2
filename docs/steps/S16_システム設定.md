# S16 — システム設定

確定日: 2026-08-14（CAS欄の2項目のみ。他の設定は必要になった時点で追加する）

運用の方針が現場ごとに違う部分を、管理者が画面から切り替えられるようにする。
値は `system_settings` テーブルに文字列で持ち、`packages/shared/src/settings.ts` で型付きに読み替える。

## 現在ある設定

| 設定 | キー | 既定 | 効果 |
|---|---|---|---|
| CAS番号を必須にする | `substance.cas_required` | **オフ** | オンにすると、CAS空欄では物質を保存できない（400） |
| CAS番号の形を強制する | `substance.cas_format_enforced` | **オフ** | オンにすると、`数字-数字-数字` でない値は保存できない（400）。オフなら警告だけ |

**既定はどちらもオフ**。ポリマー・UVCB・組成不明品・企業秘密物質を扱えるようにするため。
厳密に管理したい運用では両方オンにする。

## 動作の決めごと

1. 未設定のキーは既定値にフォールバックする。初期データの投入は不要
2. **形式を強制しているときは、形式の警告は出さない**（エラーで弾かれるため二重に出さない）
3. 必須にすると、物質の登録画面で CAS 欄に「（任意）」が消え、ブラウザ側でも必須になる
4. 設定を変えても**既存データは検証し直さない**。次に保存したときから効く
5. 設定の変更は監査ログに残す

## 権限

**設定は参照も変更もシステム管理者だけ。** 一般ユーザーには設定画面を見せない。

| 操作 | 必要な権限 |
|---|---|
| `GET /api/settings` | `ADMIN` |
| `PUT /api/settings` | `ADMIN` |
| `/admin/settings` 画面 | `ADMIN`（`app/admin/layout.tsx` のガード） |

### 一般ユーザーの画面が設定値を必要とするとき

API を緩めてはいけない。**サーバーコンポーネントで `getAppSettings()` を呼び、必要な値だけを
クライアントコンポーネントに渡す**。物質の登録・編集画面がその形になっている
（`app/substances/new/page.tsx` / `app/substances/[id]/page.tsx`）。
これなら設定一式がブラウザに渡らず、画面は設定に追従できる。

## 2026-10-02 追加: セキュリティの区分・アクセス制御・接続元の組織

### セキュリティの区分

システム設定の下のほうに見出し「セキュリティ」を置き、その下に 自動ログアウト・2要素認証・パスワード規則・パスワードの有効期限・アクセス制御（接続元IPアドレス）を並べる（利用者の指示）。

### アクセス制御（接続元IPアドレス）

| 設定のキー | 値 |
| --- | --- |
| `security.ip_filter_mode` | `off`（使わない）/ `allow`（許可リスト）/ `deny`（拒否リスト） |
| `security.ip_allow_list` | JSON。`[{ address, note }]`。200 行まで |
| `security.ip_deny_list` | 同上 |

- 書けるのは 1 つのアドレスか範囲（IPv4・IPv6 とも）。読み取りと照らし合わせは `packages/shared/src/ip-rules.ts`（画面と入口で同じもの）
- 入口（`middleware.ts`）が要求ごとに判定する。middleware は **Node.js で動かす**（DB の設定を読むため。Next.js 15.5 から）。DB は 10 秒に 1 回だけ読む（`lib/ip-filter.ts`）ので、保存から効くまで最大 10 秒
- 断るときは 404「Not Found」だけ返す（環境変数の制限と同じ）。`/api/health` と `/print/` は見ない
- 許可リスト: 相手が分からなければ断る。リストが空なら断らない（DB を手で書き換えても全員を締め出さない）
- 拒否リスト: 相手が分からなければ通す
- **締め出し防止**: 保存のとき、保存した本人のアドレスで確かめる。許可リストで本人が載っていない・本人が分からない・リストが空、拒否リストで本人が載っている、のどれかなら 400 で断る
- **戻り道**: 環境変数 `IP_RULES_OFF=1` で起動し直すと画面の設定を見なくなる（DB の値は消えない）
- 環境変数 `ALLOWED_IPS` / `IP_FILTER_MODE` による制限はそのまま残す（サーバーを置く人の決まり）。両方を通ったものだけが入れる

### 接続元の組織（JPNIC の WHOIS）

- 外から来た**日本のアドレスだけ**を JPNIC（whois.nic.ad.jp:43）に問い合わせ、組織名（日本語・英語）とネットワーク名をアクセス記録に出す（`lib/ip-whois.ts`）
- ログインを待たせない。ログインの記録のときと、アクセス記録を開いたときに裏の列へ並べ、1 件ずつ・1 秒あけて問い合わせる。8 秒で打ち切り、失敗したら 30 分あける
- 結果は表 `ip_whois` に**範囲で**ためる（同じ範囲の別のアドレスは問い合わせない）。範囲の端は桁をそろえた 16 進の文字列。JPNIC に無いアドレスは、そのアドレスだけの範囲で found=false。見つかったものは 90 日、無かったものは 30 日で調べ直す
- 外へ出るのは調べるアドレスだけ。もともとインターネット越しにつないできた相手のもの（利用者と相談して決めた）

## 2026-11-17 2要素認証が必須のときの、パスワードでのログイン

利用者の質問（「必須にしたとき、パスキーの扱いはどうなるのか」）から、穴が 1 つ見つかった。利用者の指示で直した。

- **前の動き**: 必須のとき、認証アプリかパスキーのどちらかを登録していれば「済み」と扱う（`lib/pending-step.ts`）。ここは変えていない。
  ただしパスワードでのログインは、認証アプリを登録している人にだけコードを聞き、パスキーの有無は見ていなかった。
  パスキーだけを登録した人は、必須にしていても**パスワードだけで入れた**（パスワードを知っているだけの相手が、2 つ目の確かめなしで入れる）
- **決めたこと（利用者に案を示して選んでもらった）**: 必須のとき、パスワードでのログインを次のように扱う

  | その人の登録 | パスワードでのログイン |
  | --- | --- |
  | 認証アプリあり | パスワード＋コードで入れる（今までどおり） |
  | パスキーだけ | 断る（403 `passkey_required`）。「2要素認証が必須のため、パスワードだけではログインできません。「パスキーで入る」からログインしてください。…」 |
  | どちらも無い | 入れるが、登録の画面から先へ進めない（今までどおり） |

  必須でないときは何も変えない（パスキーを持っていてもパスワードだけで入れる）。パスキーでのログインも変えない。
  「パスキーを持っていても認証アプリの登録も求める」案は、全員に認証アプリを入れてもらうことになるので採らなかった
- **断るのは、パスワードが合ったあと。**違うパスワードには、ふつうの「メールアドレスまたはパスワードが正しくありません」を返す（パスキーの有無を教えない）。
  アクセス記録には失敗の理由 `passkey_required`（画面では「パスキーが要るのにパスワードで試された」）で残る。失敗の回数には数えない（ロックの対象にしない）
- **設定の項目名**: 「2要素認証を必須にする」→「2要素認証（認証アプリまたはパスキー）を必須にする」。パスキーで足りることが、設定を入れる人にその場で伝わるように（利用者と相談して決めた）。
  言葉は「多要素認証」に改めず「2要素認証」のまま（このシステムで確かめるのは 2 つで、画面とマニュアルもこの言葉で揃っている）
- **残っている性質**: どちらも登録していない人は、パスワードだけで登録の画面まで進める（先に登録される余地）。前からの性質で、今回は変えていない。
  パスキーだけの人は、パスキーを使えない端末からは入れなくなる（断りの文とマニュアルで、認証アプリも登録するよう案内している）。
  端末を失くした人は、管理者がパスキーを外せば「どちらも無い」に戻り、パスワードで入って登録し直せる
- **直したところ**: `lib/auth.ts` の `login`（設定を先に読み、認証アプリが無くパスキーがある人を断る）、`app/api/auth/login/route.ts`、アクセス記録の理由の言葉、文言、マニュアル（「安全のしくみ」「自分用の設定」）。
  試験は `apps/web/lib/login-passkey-required.test.ts`（直す前は 1 つ落ち、直したあと 5 つ通る）
- **確かめたこと（開発環境。実際にログインを送った）**: 必須・パスキーだけ・正しいパスワード → 403 と上の文、ログインの Cookie は出ない／同じ人に違うパスワード → 401 のふつうの文／
  必須・どちらも無い → 200 で入れ、ほかの読み込みは 403（行き先 `/mfa-setup`）、自分の情報は 200／必須でない・パスキーあり → 200 で入れ、ほかの読み込みも 200／
  必須・認証アプリあり → コード待ち／アクセス記録の理由は `passkey_required` → `bad_password` の順に残る。ログイン画面に断りの文が出て、「パスキーで入る」のボタンが同じ画面にある（返事を差し替えて出方を見た）。
  設定の画面の項目名と、マニュアルの 2 ページの説明も画面で見た。使った人と設定は元へ戻した

## 2026-11-17 先に済ませる用事（パスワードの変更・2要素認証の登録）の画面への送り方

公開中の環境で、パスワードを変えた直後の人が、2要素認証の登録の画面を 37 秒のあいだに約 90 回取りに行った。利用者「90 回も開き直すのは異常であってはならないこと」。
調べて、原因と直し方を示し、了承を得て直した。

- **原因**: 外枠（`components/app-shell.tsx`。最上位の layout の中）が、別の画面へ送るのに `redirect()` を投げていた。
  layout が `redirect()` を投げた状態で、画面の中からの読み直し（`router.refresh()`）が走ると、送り先を休みなく取りに行く。
  パスワード変更の画面は、変更が済むと自分で読み直しをするので、2要素認証が必須で登録がまだの人は必ず当たっていた。ログインが切れたあとの読み直しでも同じことが起きた
- **もう 1 つの穴**: layout は、画面の中の移動（メニューを押すなど）では作り直されない。用事の画面からメニューを押すと、一覧の画面が開き、
  中身は読めず「先に済ませることがあります。案内される画面で手続きを終えてください」とだけ出て、行き先が分からなかった（本番で、システム管理者が「製品・原材料、物質が見えない」と言った原因）
- **直したこと**:
  - 外枠は、画面ごとの読み込み（ブラウザが付ける `Sec-Fetch-Dest: document`）のときだけ `redirect()` を使う。それ以外と、見分けが付かないときは、
    画面ごと読み込み直して送る部品（`components/hard-redirect.tsx`）を返す
  - 外枠は、用事の画面を枠の部品（`AppShellClient`）へ渡す。用事が残っている人がほかの画面へ移ろうとしたら、中身を出さずに、いまのアドレスを画面ごと読み込み直す。
    サーバーが、まだ用事が残っていれば用事の画面へ送り、済んでいれば（登録を終えた直後など）そのまま開く
  - 読み込みの断り（403 `pending_setup`）に、行き先をヘッダー `x-chem-pending` で載せる。画面の側（`lib/auth-redirect.ts` の `redirectIfUnauthorized`・`redirectIfPending`）は、
    これを見て用事の画面へ送る。画面を開いている途中で用事ができた人（管理者が必須にした、パスワードの期限が切れた）のため。人数の読み込み（30 秒ごと）も同じ処理を通す。
    **もう用事の画面にいるときは送らない**（用事の画面でも、枠の読み込みは同じ断りを受ける。送ると読み込み直し続ける）
- **確かめたこと（開発の環境と、本番用に組み立てたものの両方。実際に操作した）**:

  | 場面 | 直す前（開発） | 直したあと（開発・本番用の組み立て） |
  | --- | --- | --- |
  | パスワードを変えた直後に、登録の画面を取りに行く回数 | 1,405 回 | 2 回・1 回 |
  | 登録がまだの人が、一覧の画面で読み直し | 264 回 | 1 回 |
  | ログインが切れたあとの読み直しで、ログイン画面を取りに行く回数 | 55 回 | 1 回 |

  - 登録がまだの人がメニューを押す → 登録の画面に戻る。一覧の中身は 1 回も読みに行かない
  - 登録を済ませた直後にメニューを押す → その画面が開く（画面ごとの読み込み 1 回）。そのあとの移動は読み込みなしで開く
  - 画面を開いている途中で用事ができた → 次の移動で登録の画面へ。何も押さなくても 45 秒以内に送られる
  - 登録の画面・パスワード変更の画面に 65 秒いても、読み込み直さない（その間、枠の読み込みは断られている）。パスワード変更の画面からメニューを押しても、変更の画面に戻る
  - 本番用の組み立ては、`next start -p 3002` で立ち上げて同じ確認を流した（18 項目すべて通過）。確認のあと止めた
- **試験**: `apps/web/lib/auth-redirect.test.ts`（断りを受けたときの行き先。用事の画面にいるときは送らない。外枠の `redirect()` は見分けを確かめた 1 行だけ。app の下の layout.tsx は `redirect()` を使わない）
- **設定の案内文**: 「先に入にすると、まだ設定していない人が入れなくなります」は実際と違った（入れるが、登録の画面から先へ進めない）ので、
  「まだ登録していない人は、ログインのあと登録の画面から先へ進めません（認証アプリかパスキーを登録すれば使えます）」に直した

## 2026-11-17 システム設定の変更をアクセス記録に出す

利用者の指摘「システム設定の変更がアクセス記録に残ってませんね」「設定変更は重要な内容なのでアクセス記録に出して」。
「2要素認証を必須にする」をだれがいつ入にしたかを、画面では確かめられなかった（DB の記録を直に読んで分かった）。

- **前の作り**: 設定の保存は、保存したあとの全部の値を記録に残していた（`audit_logs`。entity `system_settings`、種類 `update`）。
  アクセス記録の画面は、種類で選んで出している（ログインまわりと、組成の閲覧・出力・取り込み）ので、ほかの表の更新と同じ名前の `update` は出せず、どの画面からも見られなかった
- **直したこと**:
  - 設定の保存の種類を `settings_update` にした。前からある記録も移行（`20261117210000_settings_update_action`）で同じ名前に揃えたので、過去の変更も出る
  - アクセス記録の画面に並べる。操作は「システム設定を変更」、対象は「システム設定」、内訳に**変えた項目**を出す
  - 変えた項目は、1 つ前の保存と見比べて出す（`lib/settings-history.ts`）。最初の保存と、1 つ前の記録に無い項目（あとから足した設定）は、最初の値と比べる。
    入・切の項目と数の項目は前後の値（「入 → 切」「480 → 479」）、文字や一覧の項目は変えたことだけ（「システム名（英語）（変更）」）
  - 項目の呼び名は、設定の画面の言葉に、見出しを前に付けたもの（「パスワード規則 › 最小の文字数」。`lib/setting-names.ts`）。
    設定の項目を足したら、ここに足さないと型の確認で落ちる（全部の項目を並べる型にしてある）
  - これからの保存には、どこから（接続元 IP）・何で（OS/ブラウザ）も残す。前からある記録には無いので、その欄は空
- **いっしょに変わること**: 設定の変更の記録も、アクセス記録の決まりに従う。選んだ行の削除・日数での削除で消え、システム設定の「アクセス記録を残す日数」で片づき、書き出しのファイルにも入る。
  「分析」の数え方は変わらない（ログイン・失敗・組成を見た、だけを名指しで数えている）
- **勝手に決めた点**: 文字や一覧の項目は値を出さない（接続元の一覧のように長いもの・選択肢の中の呼び名に直せないものがあるため）。何も変えずに保存した記録は「変更なし（保存のみ）」。
  「操作」の列を 150 → 170、「内訳」の列を 175 → 300 に広げた（新しい文言が読める幅）
- **確かめたこと（開発環境。実際に設定を保存した）**: 開発の DB の 96 件の記録が、移行で新しい種類に揃う／数・入切・文字の項目を変える保存と、何も変えない保存をして、
  読み込みに 4 件並び、変えた項目が意図どおり出る／だれが・どこから・何で、が残る／操作で絞れる／画面に「システム設定を変更」「システム設定」と、内訳の 4 通りの出方が出る／
  元へ戻す保存には 3 つの項目が並ぶ／確認で作った記録を、選んだ行の削除で消せる（18 項目すべて通過）。設定は元へ戻した
- **試験**: `apps/web/lib/settings-history.test.ts`（変えた項目の出し方、最初の値との比べ方、全部の項目に日本語と英語の呼び名があること）
