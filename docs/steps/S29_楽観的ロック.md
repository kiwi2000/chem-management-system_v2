# S29 楽観的ロック（同時編集の衝突）

2026-10-18 指示。「編集できるところ沢山あるから注意深く」「今後編集機能を作るときは楽観的ロックを書けることとする」。
100 名規模で同じレコードを 2 人が直したとき、後勝ちで黙って上書きしないための仕組み。

## 1. 考え方

- **止めるためでなく、見てから決めてもらうため。** 保存は止めない。食い違いを知らせ、「このまま保存する」を選べる。最後に保存した人が責任を負う
- 悲観的ロック（開いた時点で締め出す）は採らない。残ったロックの解除という運用の手間を生むため
- 衝突の単位は**レコード**。項目ごとの合成はしない（組成のように行の増減がある表では正しく合成できない）
- 入力は消さない。知らせを出したあとも画面の内容は残り、閉じて直し続けられる

組成の編集には 2026-09 から同じ仕組み（印 `stamp` と `force`）があった。それを全部の編集に広げ、**印が無い保存は断る**ようにした。

## 2. 仕組み

サーバー: `apps/web/lib/edit-stamp.ts`。画面: `apps/web/lib/stale-edit.ts`、`apps/web/components/stale-edit-notice.tsx`。

| 所 | すること |
| --- | --- |
| DTO | `stamp: string` を持つ（1 行の表は更新時刻のミリ秒 `rowStamp(row)`。複数行でひとまとまりの設定は `rowsStamp(rows)`。組成は `compositionStamp`） |
| 画面 | 読んだときの `stamp` を覚え、保存の本文に `stamp` を添える。応答が 409 `stale_edit` なら `readStaleEdit(res)` で誰が・いつを取り、`StaleEditNotice` を出す。「このまま保存する」は `force: true` を付けて送り直す。保存できたら応答の `stamp` に差し替える |
| サーバー | `parseEditStamp(body, m)`（印が無ければ 400 `stamp_required`）→ `updateMany({ where: { id, ...stampWhere(lock) }, data })` → `count === 0` なら `staleFromRow(m, いまの行)` で 409。入れ子の書き込みがあるときは対話型トランザクションの**最初**に門番の `updateMany` を置き、`StaleError` を投げて外で 409 に変える。応答に新しい `stamp` を添える |
| 検出 | `apps/web/lib/edit-stamp-coverage.test.ts`。PUT / PATCH の route.ts と、PUT / PATCH を送る画面の付け忘れを機械で止める。例外は理由つきで一覧に |

門番の `updateMany` は行をロックするので、同時に来た 2 つの保存のうち後の方は必ず食い違いになる（PostgreSQL の READ COMMITTED で、待ってから条件を評価し直す）。

### 2-1. 1 行の表（見本）

```ts
const lock = parseEditStamp(body, m);
if (lock instanceof Response) return lock;
const hit = await prisma.law.updateMany({ where: { id, ...stampWhere(lock) }, data: { ...fields, updatedBy: actor.user.id } });
if (hit.count === 0) {
  return staleFromRow(m, await prisma.law.findUnique({ where: { id }, select: STAMP_SELECT }));
}
const after = await prisma.law.findUniqueOrThrow({ where: { id }, select: { updatedAt: true } });
return Response.json({ ok: true, stamp: rowStamp(after) });
```

`updateMany` の `data` には関連の `connect` や入れ子の書き込みが書けない。それが要るときは 2-2。

### 2-2. 入れ子の書き込みがある表（製品の別名・用途の作り直しなど）

```ts
try {
  await prisma.$transaction(async (tx) => {
    const gate = await tx.product.updateMany({ where: { id, ...stampWhere(lock) }, data: { updatedBy: actor.user.id } });
    if (gate.count === 0) throw new StaleError();
    await tx.productAlias.deleteMany({ where: { productId: id } });
    await tx.product.update({ where: { id }, data: { ...base, aliases: { create: children.aliases } } });
  });
} catch (err) {
  if (err instanceof StaleError) {
    return staleFromRow(m, await prisma.product.findUnique({ where: { id }, select: STAMP_SELECT }));
  }
  throw err;
}
```

## 3. 範囲

印を要るもの: 製品・物質・組成・添付の説明・様式（本文とファイル）・画像の名前・法律・規制区分・規制クラス・法文物質名・CAS リンク・
データの版とデータソース・出典・インベントリ（頭と行）・金属換算係数・不純物の種類と免除・国・地域・言語・元素・組織・グループ・
拡張属性の項目・利用者（管理者の編集）・お知らせ・フィードバック・PRTR（頭・数量・実測）・システム設定・ランクの段。

印を要らないもの（理由は `edit-stamp-coverage.test.ts` の例外一覧）: 個人設定、本人の 2 要素認証とパスキー、取り込みの一時領域の印、判定の確認・上書き
（判定の行に更新時刻が無く、誰がいつ決めたかは決定の記録に残る。最後に確認した人の判断が勝つ）。

## 4. 作りながら決めたこと（勝手に決めた点）

1. **印が無い保存は 400 で断る**（組成はこれまで省略を許していた）。画面の付け忘れを黙って通さないため。外から API を呼ぶものは無い
2. **「このまま保存する」は残す。** 止める仕組みにしない（2026-10-18 の方針どおり）
3. 複数行でひとまとまりの設定（システム設定・ランクの段）は、行の更新時刻のいちばん新しいものと行数を印にする。門番は比べてから保存（行のロックは使わない。管理者だけが触るので十分）
4. 様式のファイルの差し替え（本文がファイルそのもの）は、印を URL の `?stamp=` で受ける
5. PRTR の頭（所属 × 年度で upsert）は、行があるときだけ印を要る

## 5. 残り

- 「◯◯さんが編集中」の表示（衝突を起きる前に避ける補助）は、使われ方を見てから
- 判定の確認・上書きに印を入れるなら、判定の行に更新時刻を足してから

## 6. 確かめたこと（2026-10-18、開発環境）

- 付け忘れの検出（`edit-stamp-coverage.test.ts`）: 更新の API 44 本（理由つきの例外 8）と、保存する画面 44 か所（例外 10）を走査して全部通過。全試験（651 件ほか）・型検査・lint も通過
- API（curl）: システム設定・ランクの段・国・法律・金属換算係数・組成で、印なし → 400 `stamp_required`、古い印 → 409 `stale_edit`（誰が・いつ入り）、
  正しい印 → 200 と新しい印、同じ印の使い回し → 409、`force` → 200
- 画面（Playwright）:
  - システム設定: 開いたあとに別の保存が入ると、保存で知らせが出る。「このまま保存する」で通り、その後の保存は食い違わない
  - 地域（行内編集）: 鉛筆で開いたあとに別の保存が入ると、保存で知らせが出て、「このまま保存する」で通って編集が閉じる
  - 製品（2 人の利用者を真似る）: A が備考の編集を始め、B が備考を保存し、A が保存すると知らせ（B の名前と時刻）。A の「このまま保存する」で A の内容が残る
  - 組成: 印を送って保存できる（200、新しい印）
- 作りの直し: product-form が印を持っていないときに保存の直前で読み直す作りになっていたので、既存の製品では読み直さない（読み直すとほかの人の変更を見逃す）。
  新規登録の途中の段だけ読む

実装は 3 つの下請け（マスタ群／法規制データ群／製品・物質・帳票・PRTR 群）に分けて並行し、土台・設定・ランクの段・検出の試験・確認は本体で行った。
