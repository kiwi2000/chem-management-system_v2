社内サーバーへの導入

第1章　システムの構成

サーバー1台の中で、3つのコンテナ（Docker が管理する、役割ごとの入れ物）が分かれて動きます。 社内LANに開いているのは入口のひとつだけです。

それぞれの役目
コンテナ役目社内LANから
caddy社内LANからの接続を受け、暗号化（HTTPS）して app へ渡します。社内用の証明書もここで作ります見えます（443 / 80）
app画面の表示と法規制の判定。帳票の PDF も作り、app-data に置きます見えません
db物質・製品・法規制・記録の保管。PostgreSQL 16。中身は db-data に置きます見えません

POINT

  • データはコンテナの外に置いてあります（db-data・app-data）。アプリを新しくしてコンテナを作り直しても、中身は消えません
  • 認証も自前で持っているため、外部のサービスを使いません。動いている間、社内LANの外との通信はありません

2

OSの更新Ubuntu Server 24.04 の例

# パッケージを最新にし、セキュリティ更新を自動で当てる設定にします
sudo apt update && sudo apt -y upgrade
sudo apt -y install unattended-upgrades

RHEL系の場合は sudo dnf -y update と sudo dnf -y install dnf-automatic です。

3

Docker の導入アプリとデータベースはこの上で動きます

# インターネットに繋がる場合
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
# ここで一度ログインし直します（グループの変更を反映するため）

OFFLINE（インターネットに繋がらないサーバー）

Docker の公式のパッケージ（docker-ce・docker-ce-cli・containerd.io・docker-compose-plugin）を別の機械で入手し、サーバーに入れてください。 Ubuntu の標準のパッケージを使う場合は、docker.io と docker-compose-v2 の2つが要ります。

このシステムのコンテナの記録は、1つあたり 10MB × 3 までに抑える設定にしてあります。

# 入ったことの確認。バージョンが2つとも表示されればOK
docker --version
docker compose version
4

通信の入口の制限社内LANからだけ入れるようにします

CAUTION

インターネットに向けて 80 / 443 を開けないでください。このシステムは社内LANの中だけで使う前提で作ってあります。 社外から使う必要がある場合は、御社の VPN で社内LANに入ってから開いてください。 

# SSH 以外を閉じます（Ubuntu の例。RHEL系は firewalld で同じことをします）
sudo ufw allow 22/tcp
sudo ufw enable

Docker とファイアウォール

Docker が開けた 80 / 443 には、ufw の制限が効きません（Docker が自分で通り道を作るため）。 入口を絞るときは、次のどちらか、または両方を使ってください。どちらも手順6で作る設定ファイルに書きます。

  • サーバーの社内LAN側のアドレスでだけ待つ: HTTP_PORT=192.168.10.5:80、HTTPS_PORT=192.168.10.5:443（サーバーのIPに読み替え）
  • アプリの側で、決まった範囲からだけ受け付ける: ALLOWED_IPS（手順6）

第3章　アプリの配置と起動

5

ファイルの展開お渡しした tar.gz をサーバーのホームに置いてから

sudo mkdir -p /opt/chem && sudo chown $USER /opt/chem
tar xzf ~/chem-system-(ver).tar.gz -C /opt/chem
cd /opt/chem
6

設定ファイルの作成データベースのパスワードと、入口の制限を決めます

cp .env.prod.example .env.prod
openssl rand -hex 24           # 出てきた文字列（英数字48文字）を控えます
nano .env.prod                 # DB_PASSWORD= の右側に貼り付けます

IMPORTANT

DB_PASSWORD は必ず変更してください。英数字だけにしてください（/ + @ などが入ると、アプリがデータベースに繋がりません）。 この値は最初の起動でデータベースに焼き付きます。あとから変えるにはデータベースを作り直すことになります。

.env.prod で決められること（DB_PASSWORD のほかは任意）
項目意味
HTTP_PORT / HTTPS_PORT待ち受けるポート。サーバーのIP:443 のように書くと、そのアドレスでだけ待ちます（手順4）
ALLOWED_IPS接続を受け付けるアドレスの範囲（例 192.168.10.0/24）。空なら制限しません
IP_FILTER_MODEmonitor（範囲外を記録するだけ）で様子を見て、問題が無ければ enforce（範囲外を断る）に
IP_RULES_OFFアプリの画面で決めた接続の制限で入れなくなったときだけ 1 にします（画面の制限を見なくなる。画面で直したら外す）

.env.prod を直したあとは docker compose -f compose.prod.yml --env-file .env.prod up -d で作り直してください（restart では新しい値が効きません）。 ALLOWED_IPS で締め出されたときは、空に戻して同じく作り直します。

7

起動その場で組み立てる場合、初回は10〜20分かかります

# インターネットに繋がる場合（その場でイメージを組み立てます）
docker compose -f compose.prod.yml --env-file .env.prod up -d --build

OFFLINE

お渡しした Docker イメージのファイルから読み込みます。--build は付けません。

docker load -i ~/chem-images-(ver).tar
docker compose -f compose.prod.yml --env-file .env.prod up -d
# 3つとも running になっていれば起動しています
docker compose -f compose.prod.yml --env-file .env.prod ps

CHECK

db / app / caddy の3つが running と表示されること。データベースの表は、起動のときに自動で作られます。

第4章　最初の管理者の作成

8

最初の管理者の作成

cd /opt/chem
docker compose -f compose.prod.yml --env-file .env.prod exec app \
  npx tsx scripts/set-password.ts admin@example.co.jp 'ここに12文字以上の強いパスワード' --create

メールアドレスは御社のものに読み替えてください。この1人だけコマンドで作ります。2人目からは画面から追加できます。 この管理者にはすべての権限が付きます。パスワードは12文字以上が要ります。

CAUTION

コマンドに書いたパスワードは端末の履歴に残ります。実行後に history -c で消してください。 このパスワードは、ログイン後に本人が画面から変えられます。 同じコマンドは、パスワードを忘れたときや、ログインのロックを外すときにも使えます（--create を付けずに実行）。

第5章　社内パソコンからの接続

9

ブラウザからの接続と証明書

社内のパソコンから https://サーバーのIPアドレスか名前/ を開きます。ログイン画面が出れば、ここまでは成功です。 ブラウザは Microsoft Edge か Google Chrome の最新版をお使いください。

初回は「この接続ではプライバシーが保護されません」のような警告が出ます。社内専用のため、サーバーが自分で作った証明書を使っているためで、 通信は暗号化されています。警告を消すには、サーバーのルート証明書を各パソコンに登録します（図2）。 

# サーバーで実行して、ルート証明書をファイルに取り出します（/opt/chem に chem-root.crt ができます）
cd /opt/chem
docker compose -f compose.prod.yml --env-file .env.prod exec -T caddy \
  cat /data/caddy/pki/authorities/local/root.crt > chem-root.crt

# 管理者のパソコン（Windows の PowerShell）でサーバーから受け取ります
scp chemadmin@サーバーのIP:/opt/chem/chem-root.crt .

# 各パソコンで、管理者として登録します（グループポリシーで配る場合は不要）
certutil -addstore Root chem-root.crt

CHECK

社内のパソコンで、ブラウザをすべて閉じて開き直し、https://名前/ で警告が出ずにログイン画面が出ること。手順8で作った管理者でログインできること。

第6章　毎日のバックアップ

サーバーが壊れたときに戻すために守るものは、次の図のとおりです。設定ファイルとデータベースのバックアップの2つがあれば、新しいサーバーで同じ状態に戻せます。 帳票の PDF と証明書の元は、無くても動きますが、残しておくと手間が減ります。

10

自動バックアップの設定これは必ず設定してください

# バックアップと記録の置き場所を、作業するユーザーが書ける形で先に作ります
sudo install -d -o $USER /var/backups/chem
sudo install -o $USER /dev/null /var/log/chem-backup.log
crontab -e

開いたファイルの最後に、次の1行を足して保存します（毎日 深夜3時）。

0 3 * * * bash /opt/chem/scripts/backup-db.sh >> /var/log/chem-backup.log 2>&1

/var/backups/chem/ に chem_年月日_時分秒.sql.gz が1日1つ増えます。14日より古いものは自動で消えます。 （bash を付けて呼ぶと、ファイルの実行権に関係なく動きます）

IMPORTANT

サーバーとは別の機器へ複製してください。同じサーバーの中だけに置いていると、サーバーが壊れたときにデータも一緒に失われます。 社内NASへ毎日コピーする設定を、cron に別の行として足してください（例: 4時に rsync -a /var/backups/chem/ NASのマウント先/chem/）。 backup-db.sh の中に書き足すと、アプリの更新で元に戻ります。

帳票の PDF も残す場合

docker volume inspect chem_app-data の Mountpoint に出るフォルダーも、NAS への複製の対象に入れてください（読むには sudo が要ります）。

CHECK

その場で1回動かして、ファイルができることを確かめます。

bash /opt/chem/scripts/backup-db.sh
ls -lh /var/backups/chem/

第7章　導入完了の確認

次のすべてができていれば、導入は完了です。

  • docker compose -f compose.prod.yml --env-file .env.prod ps で3つとも running になっている
  • 社内のパソコンから https://サーバーの名前かIP/ で、警告なしにログインできる
  • バックアップのファイルが /var/backups/chem/ にでき、NAS にも複製されている
  • .env.prod の控えを、サーバーの外に保管した
  • サーバーを再起動しても、自動でアプリが立ち上がる（sudo reboot で確認）

法規制のデータ（法律・規制区分・法文物質名と CAS 番号のリンク）は、この手順では入りません。 物質や製品のデータも空の状態です。法規制のデータは導入のときにこちらが入れます。入るまで、判定は動きません。

第8章　導入後の運用・復元

定期的にお願いすること
いつすることやりかた
毎日バックアップの確認前日のファイルが /var/backups/chem/ と NAS にあるか。/var/log/chem-backup.log に失敗が出ていないか（Windows は C:\chem\logs\backup.log）
毎月ディスクの空きを見るdf -h。使用率80%を超えたらご連絡ください
更新のあと古いイメージの片付けdocker image prune -f（更新のたびに前の版のイメージが残るため）
年1回アクセス記録の整理画面から古い分を削除します。自動では消えません（やり方はユーザーマニュアル）

アプリの更新は第11章を見てください。

バックアップからの復元

復元は、データベースの中身をバックアップを取った時点の内容に置き換えます。それ以降に入れたものは消えます。先にアプリを止めてから行います。 

cd /opt/chem
docker compose -f compose.prod.yml --env-file .env.prod stop app
gunzip -c /var/backups/chem/chem_年月日_時分秒.sql.gz | \
  docker compose -f compose.prod.yml --env-file .env.prod exec -T db psql -U chem chem
docker compose -f compose.prod.yml --env-file .env.prod start app

サーバーが壊れたとき（新しいサーバーで戻す）

  1. 新しいサーバーで手順1〜5を行う
  2. 手順6の代わりに、控えておいた .env.prod を /opt/chem/ に置く（パスワードが同じでないと戻せません）
  3. 手順7で起動する
  4. NAS から一番新しいバックアップを持ってきて、上の「復元」を行う
  5. 手順9（証明書）・手順10（バックアップ）を行う。証明書の元を残していなければ、各パソコンに配り直す

所要の目安は1時間ほどです。

第9章　うまくいかないとき

症状見るところ
ブラウザで開けないdocker compose -f compose.prod.yml --env-file .env.prod ps で3つとも running か。.env.prod の HTTPS_PORT・ALLOWED_IPS で、そのパソコンが外れていないか
「データベースに接続できません」と出るdocker compose -f compose.prod.yml --env-file .env.prod logs db。DB_PASSWORD を後から変えていないか、英数字以外が入っていないか
ログインできない続けて間違えると一時的にロックされます。しばらく待つか、手順8のコマンド（--create なし）でパスワードを出し直してください
証明書の警告が消えないルート証明書を「信頼されたルート証明機関」に入れたか。ブラウザをすべて閉じて開き直したか
動きが遅いfree -h でメモリの空き、df -h でディスクの空き
アプリの記録を見たいdocker compose -f compose.prod.yml --env-file .env.prod logs -f app

SUPPORT

解決しない場合は、実行したコマンドと、画面に出たメッセージをそのままお送りください。 docker compose -f compose.prod.yml --env-file .env.prod logs --tail 200 app の出力もあわせていただけると、原因を絞り込めます。

第10章　Windows Server への導入 Linux の代わりに

Windows Server に入れる場合は、第2章〜第9章の代わりにこの章を使います。アプリのプログラムは Linux 版と同じです。 違うのは、Docker の代わりに3つを Windows のサービスとして常駐させるところです。 必要なソフトはすべてインストールセットに入れてお渡しするので、サーバーがインターネットに繋がっていなくても導入できます。

IMPORTANT

仮想化（Hyper-V・WSL2・Docker）は使いません。Windows Server 2019 / 2022 / 2025 のいずれかで、管理者権限が要ります。 この構成は Linux 版ほどの運用実績がありません。どちらでもよい場合は Linux 版をお勧めします。

10-1

セットの照合と展開C:\chem-install に置きます

お渡しした zip と .sha256 をサーバーの C:\ にコピーし、管理者の PowerShell で次を実行します。 1行目の出力と .sha256 の中身が同じなら、ファイルは壊れていません。 

(Get-FileHash C:\chem-install-set-(ver)-win64.zip).Hash.ToLower(); Get-Content C:\chem-install-set-(ver)-win64.zip.sha256
tar -xf C:\chem-install-set-(ver)-win64.zip -C C:\
Rename-Item C:\chem-install-set-(ver)-win64 C:\chem-install

ファイルが多いので、Windows に入っている tar で展開します（Expand-Archive は 10 分近くかかります）。

先に確かめること

  • 80 / 443 番を使うソフトが動いていないこと（IIS など）。動いていると入口が起動しません
  • Node.js がすでに入っている場合は、版が 24 であること。別の版が入っていると、導入は止まってお知らせします（入っていなければ、セットのものを入れます）
  • 時刻が合っていること（記録の時刻、バックアップ、2要素認証に影響します）
10-2

導入の実行10〜15分かかります

管理者の PowerShell で次を実行します。社内LANのアドレス範囲と、最初の管理者（画面にログインする方）のメールアドレスを御社のものに変えてください。

powershell -ExecutionPolicy Bypass -File C:\chem-install\scripts\install.ps1 `
  -LanCidr 192.168.10.0/24 -AdminEmail admin@example.co.jp

途中で3つのパスワードを聞かれます。打った文字は画面に出ず、どこにも記録されません。

聞かれるもの何のパスワードか控え
postgresデータベースの管理ユーザー。データベースそのものの保守で使います必ず控える
chemアプリがデータベースに繋ぐためのもの。C:\chem\.env に書き込まれます。復元にも使います控える（.env にも残ります）
最初の管理者画面にログインするためのもの。全権限が付きます。ログイン後に本人が画面から変えられます本人に渡す

CAUTION

パスワードは 12文字以上で、英数字だけにしてください（記号が入ると、設定ファイルの読み取りや、データベースへの接続が崩れることがあります）。

スクリプトは次の順に進みます。画面にはこの見出し（W1〜W8）が出ます。

画面に出る見出し
見出しすること
W1 前提ソフトNode.js 24・Visual C++ ランタイム・PostgreSQL 16（ポート 5432、pgAdmin は入れません）・Caddy・NSSM を入れます。入っているものは飛ばします
W2 データベースとユーザー業務用のユーザー chem とデータベース chem を UTF-8 で作ります
W3 アプリの配置app\ を C:\chem に写し、C:\chem\.env を作ります（管理者と SYSTEM だけが読めます）
W4 データベースの表データベースの表を作ります
W5 最初の管理者指定したメールアドレスで、全権限の利用者を1人作ります

W7 通信の入口指定したLANからの 443（HTTPS）と 80（HTTPS へ転送）だけを開けます。データベースは開けません
W8 毎日のバックアップ毎日3時に C:\backups\chem へ取るタスクを登録し、その場で1回取ります

CHECK

最後の「状態」で、chem-app・chem-caddy・postgresql-x64-16 が Running / Automatic、https://127.0.0.1/api/health が 200 と {"ok":true,"db":"up"} であること。

途中で止まったら、表示された原因を直してから同じコマンドをもう一度実行してください。済んだところは飛ばします。

10-3

社内パソコンからの接続名前と証明書

サーバーには名前で開くようにしてください（例 chem.example.local）。社内の DNS に登録するか、 各パソコンの C:\Windows\System32\drivers\etc\hosts に 192.168.10.5 chem.example.local のように1行足します。

証明書の流れは Linux 版と同じです（第5章の図2）。ルート証明書はサーバーの C:\ProgramData\caddy\pki\authorities\local\root.crt にあります。共有フォルダーなどで各パソコンに配り、登録します。 

certutil -addstore Root root.crt      # 各パソコンで、管理者として（グループポリシーで配る場合は不要）

HTTPS で開いてください

ログインの記録はHTTPS のときだけ保たれる作りです。http:// や :3001 で直接開かず、必ず https://名前/ で開いてください。 パスキー（指紋や顔でのログイン）は、名前で開き、証明書の警告が出ていないときだけ使えます。

CHECK

社内パソコンでブラウザをすべて閉じて開き直し、https://名前/ を警告なしで開けること。10-2 で決めた管理者でログインできること。

10-4

状態の確認とバックアップの複製いつでも使えます

powershell -ExecutionPolicy Bypass -File C:\chem\deploy\windows\check.ps1

サービスの状態、アプリの応答、記録の末尾、空き容量をまとめて出します。困ったときは、この出力をそのままお送りください。

IMPORTANT

バックアップ（C:\backups\chem\chem_年月日_時分秒.sql.zip）を、社内NASなど別の機器へ毎日複製してください。 タスクスケジューラに別のタスクを作り、robocopy C:\backups\chem \\NAS\共有\chem /E のように写すのが簡単です （C:\chem\scripts\backup-db.ps1 に書き足すと、更新で元に戻ります）。 タスクを SYSTEM で動かす場合、NAS 側ではサーバーのコンピューター アカウントに書き込みを許してください。

Windows Server ならではの注意

項目すること
Windows Update再起動の時間帯を業務時間の外に設定してください。サービスは自動起動なので、再起動しても戻ります
ウイルス対策C:\chem・C:\Program Files\PostgreSQL\16\data・C:\backups\chem をリアルタイム検査の対象外にすることを検討してください。データベースの書き込みが遅くなることがあります
守るもの第6章の図3のとおり。C:\chem\.env（設定。控えをサーバーの外へ）と、毎日のバックアップ（NAS へ複製）。帳票の PDF（C:\chem\data\documents。画面の設定で別のフォルダーにもできます）と証明書の元（C:\ProgramData\caddy）は、残すなら複製してください。帳票の PDF は更新では消えません
記録アプリは C:\chem\logs\chem-app.log（10MB で切り替わります）。毎日のバックアップは C:\chem\logs\backup.log に、成功も失敗も1行ずつ残ります
締め出されたときアプリの画面で決めた接続の制限で入れなくなったときは、C:\chem\.env に IP_RULES_OFF=1 の1行を足し、管理者の PowerShell で C:\chem\nssm\nssm.exe restart chem-app。画面で直したら、その行を消してもう一度 restart します
パスワードを忘れた・ロックされた管理者の PowerShell で次の3行（1行目は設定ファイルからデータベースの接続先を読む）。
cd C:\chem
$env:DATABASE_URL = (Select-String -Path .env -Pattern '^DATABASE_URL="?([^"]+)').Matches[0].Groups[1].Value
npx tsx scripts/set-password.ts メールアドレス '新しいパスワード'

バックアップからの復元（Windows Server）

データベースの中身を、バックアップを取った時点に置き換えます。それ以降に入れたものは消えます。管理者の PowerShell で行います。

C:\chem\nssm\nssm.exe stop chem-app
Expand-Archive C:\backups\chem\chem_年月日_時分秒.sql.zip -DestinationPath C:\backups\restore
$env:PGPASSWORD = 'chem のパスワード'    # 10-2 で控えたもの（C:\chem\.env の DATABASE_URL にも入っています）
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -h 127.0.0.1 -U chem -d chem -f C:\backups\restore\chem_年月日_時分秒.sql
C:\chem\nssm\nssm.exe start chem-app

サーバーが壊れたときは、新しいサーバーで 10-1〜10-2 を行い（chem のパスワードは前と同じにする）、そのあと上の復元を行います。

第11章　更新の手順 場合ごと

導入したあとに何かを新しくするときの手順です。何を新しくするかで手順が違います。 お渡しする「更新のご案内」に、どの場合に当たるかを書いてあります。案内が無いときは、届いたファイルの名前で見分けてください。

3つの場合
場合届くものアプリが止まる時間作業のあとの「判定し直し」
11-1 プログラムの更新
（データベースの構造は変わらない）		アプリのセット（chem-system-(ver).tar.gz / chem-install-set-(ver)-win64.zip）Linux 1〜3 分（組み立ての間は動いています）、Windows 数分案内に書いてあるときだけ
11-2 プログラムの更新
（データベースの構造が変わる）		同上。案内に「データベースの構造が変わります」と書いてあります同上＋1 分ほど案内に書いてあるときだけ
11-3 データの更新データセット（chem-data-set-(日付).zip）。法規制データの新しい版、法律の改正など止まりません必ず行う

どの場合にも共通のこと

いつすること
前利用者に「何時から何分止まる／判定が一時的に古くなる」と知らせる
前バックアップを取る。Linux は bash /opt/chem/scripts/backup-db.sh。Windows はプログラムの更新なら update.ps1 が自動で取ります。データだけの更新のときは管理者の PowerShell で powershell -ExecutionPolicy Bypass -File C:\chem\scripts\backup-db.ps1
後ログインして、ユーザーマニュアルの「変更履歴」の先頭が新しい版になっていることを見る（プログラムの更新のとき）
後アプリが動いていることを確かめる。Linux は docker compose -f compose.prod.yml --env-file .env.prod ps（3 つとも running）、Windows は check.ps1（Running と 200）

11-1・11-2 プログラムの更新（Linux）

新しい版は新しいフォルダーに展開して入れ替えます（前の版のファイルが混ざらないように。前の版は戻すときのために残します）。 データベースの構造が変わる版でも、起動のときに自動で当たります。 

# ① バックアップ
bash /opt/chem/scripts/backup-db.sh

# ② 新しい版を別のフォルダーに展開し、設定ファイルを写してから入れ替える
sudo mkdir /opt/chem-new && sudo chown $USER /opt/chem-new
tar xzf ~/chem-system-(ver).tar.gz -C /opt/chem-new
cp /opt/chem/.env.prod /opt/chem-new/
sudo mv /opt/chem /opt/chem-old-$(date +%Y%m%d)
sudo mv /opt/chem-new /opt/chem

# ③ 起動（組み立て 10〜20 分。止まるのは最後の 1〜3 分）
cd /opt/chem
docker compose -f compose.prod.yml --env-file .env.prod up -d --build
#   インターネットに繋がらない場合は、--build の代わりに先に読み込む
#   docker load -i ~/chem-images-(ver).tar && docker compose -f compose.prod.yml --env-file .env.prod up -d

# ④ 確認のあと、前の版のイメージを片付ける
docker compose -f compose.prod.yml --env-file .env.prod ps
docker image prune -f

保存領域（データベース・帳票の PDF・証明書）は、フォルダーの名前が同じ chem なので、そのまま引き継がれます。うまく動くことを確かめてしばらくしたら、/opt/chem-old-日付 は消して構いません。

11-1・11-2 プログラムの更新（Windows Server）

# 管理者の PowerShell で。前の版の展開フォルダーを消してから、新しいセットを展開する（前の版の zip は戻すときのために残す）
Remove-Item -Recurse -Force C:\chem-install
tar -xf C:\chem-install-set-(ver)-win64.zip -C C:\
Rename-Item C:\chem-install-set-(ver)-win64 C:\chem-install
powershell -ExecutionPolicy Bypass -File C:\chem-install\scripts\update.ps1

update.ps1 は、いま入っている版と届いた版を比べて「データベースの表が変わります／変わりません」を先に表示し、 バックアップを取り、アプリを止め、ファイルを入れ替え、表に足りない変更があれば足し、アプリを起動して状態を出します。数分で終わります。 設定（.env）・記録・バックアップ・作った帳票の PDF は残ります。

戻すとき

  • 11-1（構造が変わらない版）: 前の版で ②③ をやり直します。Linux は /opt/chem と /opt/chem-old-日付 の名前を入れ替えて up -d --build、Windows は前の版の zip で上の手順を行います。データベースはそのままで大丈夫です。
  • 11-2（構造が変わった版）: 前の版のプログラムをそのまま戻しても動きません。前の版に入れ替えたあと、① で取ったバックアップから復元してください（Linux は第8章、Windows は第10章の「復元」）。更新のあとに入れた記録は消えます。

11-3 データの更新

プログラムは変えません。届いたデータセットを、システム管理者が画面から取り込み、全製品を判定し直します。作業中もアプリは止まりません。 画面の操作はユーザーマニュアルの「データを出し入れする」に、その回の注意は「更新のご案内」にあります。

  • 取り込みには、取り込みの権限を持つ管理者が要ります。導入のとき（手順8・10-2）に作った管理者には付いています。
  • 取り込みは足す・直すだけで、消しません。御社が画面で足したデータは残り、届いたデータより優先されます。
  • 判定し直しは、製品が数百件なら数分です。終わったら、代表的な製品を 1〜2 件開いて、案内どおりの結果になっていることを見てください。

CAUTION

古い規制区分を消さないでください。区分を消すと、その区分の判定結果（確認済みの印を含む）も一緒に消えます。改正で使わなくなった区分は、適用終了日で区別してあります。
